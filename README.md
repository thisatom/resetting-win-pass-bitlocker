## 1. Введение

BitLocker — встроенная в операционные системы Microsoft Windows технология полнотомного шифрования дисков. Она предназначена для защиты информации от несанкционированного доступа в случае потери устройства, кражи накопителя или попытки прочитать данные за пределами штатной операционной системы.

В основе BitLocker лежит многоуровневая система управления криптографическими ключами. Данные на диске шифруются симметричными алгоритмами, а доступ к ключевому материалу контролируется дополнительными механизмами защиты: TPM, PIN-кодом и паролем восстановления.

Однако у полнотомного шифрования есть фундаментальная особенность: **после разблокировки тома операционная система должна выполнять операции чтения и записи без повторной аутентификации при каждом обращении к накопителю.** Поэтому необходимый для работы криптографический материал становится доступен системным компонентам и может присутствовать в оперативной памяти.

Это представляет интерес для специалистов по информационной безопасности и цифровой криминалистике. Исследование оперативной памяти позволяет изучать состояние криптографических подсистем, работу драйверов и особенности управления ключевыми данными. Особенно интересны такие исследования в контексте Windows 11, поскольку внутренние структуры памяти и механизмы взаимодействия системных компонентов меняются между версиями ОС.

## 2. Архитектура BitLocker

Для понимания особенностей исследования оперативной памяти необходимо разобраться в принципах организации криптографической системы BitLocker. В отличие от простого шифрования файлов, BitLocker использует иерархию ключей, позволяющую разделить непосредственное шифрование данных и управление доступом к ним.

### 2.1. Иерархия криптографических ключей

В архитектуре BitLocker используются несколько типов ключей:

- **FVEK (Full Volume Encryption Key)** — ключ шифрования тома. Непосредственно участвует в шифровании и расшифровке данных на накопителе.
- **VMK (Volume Master Key)** — мастер-ключ тома. Защищает FVEK и управляет доступом к ключу шифрования данных.
- **Key Protectors** — механизмы защиты VMK. Определяют условия, при которых ОС может получить доступ к защищённому ключевому материалу.

В зависимости от конфигурации могут использоваться:

- TPM;
- TPM + PIN;
- пароль восстановления;
- пароль пользователя;
- стартовый ключ на USB-носителе.

Общая схема:

```text
             Key Protectors
                   |
                   v
                  VMK
                   |
                   v
                  FVEK
                   |
                   v
          Шифрование данных тома
```

Таким образом, TPM и другие механизмы защиты не обязательно непосредственно шифруют каждый сектор диска. Их задача — обеспечить контролируемый доступ к ключевой иерархии.

### 2.2. Алгоритмы шифрования

BitLocker поддерживает несколько алгоритмов. Наиболее распространённые:

| Алгоритм | Размер одного ключевого компонента | Суммарный размер |
| --- | --- | --- |
| AES-128-CBC | 128 бит | 128 бит |
| AES-256-CBC | 256 бит | 256 бит |
| XTS-AES-128 | 128 бит | 256 бит |
| XTS-AES-256 | 256 бит | 512 бит |

В режиме XTS используются два независимых ключа: один для преобразования данных, другой для вычисления tweak. Поэтому суммарный размер ключевого материала в XTS вдвое больше размера одного компонента.

Для современных установок Windows характерно использование XTS-AES-128, если политика организации или пользовательская конфигурация не задают другой алгоритм.

> **Важно:** конкретную конфигурацию всегда необходимо проверять по метаданным исследуемого тома.

### 2.3. Компоненты Windows, участвующие в работе BitLocker

| Компонент | Назначение |
| --- | --- |
| `fvevol.sys` | Драйвер управления зашифрованными томами |
| `ksecdd.sys` | Компонент инфраструктуры безопасности ядра |
| CNG | Криптографическая инфраструктура Windows |
| SymCrypt | Криптографическая библиотека Microsoft |
| `dumpfve.sys` | Компонент обработки аварийных дампов зашифрованных томов |

Взаимодействие этих компонентов обеспечивает выполнение криптографических операций, управление ключевым материалом и обработку операций ввода-вывода. Внутреннее устройство компонентов может меняться между сборками Windows.

## 3. Ключевой материал в оперативной памяти

### 3.1. Почему ключи присутствуют в RAM

Полнотомное шифрование должно обеспечивать прозрачную работу ОС с данными. Когда том разблокирован, Windows должна выполнять чтение и запись без повторной аутентификации, поэтому необходимые криптографические данные становятся доступны системным компонентам.

В процессе работы соответствующая информация может присутствовать:

- в памяти ядра;
- в структурах системных драйверов;
- во временных криптографических объектах;
- в промежуточных буферах;
- в областях памяти, ранее использовавшихся криптографическими компонентами.

Это не означает, что все копии ключевого материала постоянно находятся в одном месте или имеют одинаковый срок жизни.

### 3.2. Управление временем жизни криптографических данных

Microsoft использует собственную криптографическую инфраструктуру SymCrypt. Она предоставляет механизмы создания криптографических объектов, управления сессиями и освобождения связанных ресурсов.

Однако **освобождение объекта не всегда означает немедленное физическое обнуление соответствующей области памяти.** После освобождения память может оставаться доступной для повторного использования другими компонентами ОС.

На особенности хранения данных влияют:

- время жизни криптографического объекта;
- механизм выделения памяти;
- повторное использование буферов;
- оптимизации криптографических операций;
- поведение драйверов;
- особенности конкретной версии Windows.

Поэтому при исследовании дампов важно учитывать не только активные объекты, но и общую структуру памяти.

### 3.3. Особенности разных версий Windows

Внутренние структуры памяти Windows менялись на протяжении развития ОС. В исторических исследованиях BitLocker упоминаются:

- **Windows 7** — структуры, связанные с драйвером `fvevol.sys`;
- **Windows 8, 8.1 и 10** — более тесная интеграция с криптографической инфраструктурой CNG;
- **Windows 11** — дальнейшие изменения внутренних структур и взаимодействия системных компонентов.

Для Windows 11 особенно важно учитывать номер сборки. Нельзя автоматически переносить результаты исследования Windows 10 на Windows 11 или считать, что одна и та же структура памяти будет одинаковой во всех выпусках Windows 11.

## 4. Получение дампа оперативной памяти

### 4.1. Назначение и особенности дампов

Дамп оперативной памяти — это снимок содержимого физической памяти компьютера на определённый момент времени. В цифровой криминалистике он используется для исследования:

- запущенных процессов и потоков выполнения;
- объектов ядра и загруженных драйверов;
- сетевых соединений;
- системных структур и временных данных;
- состояния криптографических компонентов.

В отличие от анализа файловой системы, исследование RAM позволяет изучать состояние системы во время её работы. Это особенно важно при анализе инцидентов, связанных с компрометацией работающего устройства.

### 4.2. Инструменты исследования

- **[Memory-Dump-UEFI](https://github.com/NoInitRD/Memory-Dump-UEFI)** — проект для работы с физической памятью через UEFI.
- **[Volatility 3](https://github.com/volatilityfoundation/volatility3)** — открытая платформа анализа дампов оперативной памяти; позволяет исследовать процессы, модули, структуры ядра и другие артефакты.
- **[WinDbg](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/)** — отладчик Microsoft для анализа дампов Windows и исследования структур ОС.
- **[PoolMonX](https://github.com/zodiacon/PoolMonX)** — инструмент исследования использования пулов памяти Windows.

Выбор инструмента зависит от формата дампа, версии ОС и поставленной исследовательской задачи.

### 4.3. Ограничения UEFI и Secure Boot

Secure Boot проверяет доверенность компонентов, участвующих в загрузке. Он ограничивает запуск неподписанных или неразрешённых компонентов, что может влиять на использование сторонних UEFI-инструментов.

При исследовании необходимо учитывать:

- конфигурацию Secure Boot;
- используемые ключи доверия;
- настройки UEFI;
- поддержку конкретного оборудования;
- совместимость исследовательского ПО.

Отключение защитных механизмов загрузки без необходимости не рекомендуется. Для криминалистического исследования следует использовать документированную и согласованную процедуру получения данных.

### 4.4. Сохранение целостности доказательств

Дамп оперативной памяти является цифровым доказательством, поэтому его сохранность имеет принципиальное значение. Рекомендуется фиксировать:

- дату и время получения;
- модель оборудования и версию BIOS/UEFI;
- объём оперативной памяти;
- версию операционной системы;
- использованный инструмент и формат дампа;
- контрольные суммы исходных файлов.

Для проверки целостности можно использовать SHA-256. Например, в Linux:

```bash
sha256sum memory-dump.raw
```

Контрольная сумма позволяет убедиться, что файл не изменился после получения. Исходный дамп желательно хранить отдельно от рабочих копий, используемых при анализе.

## 5. Анализ памяти Windows

### 5.1. Пулы памяти ядра

Windows использует несколько механизмов управления памятью. Одним из них являются **пулы ядра**: они позволяют системным компонентам и драйверам выделять память для временных и постоянных структур.

Среди основных типов выделяют:

- **NonPaged Pool** — память, которая не может быть выгружена на диск;
- **Paged Pool** — память, страницы которой могут быть перемещены в файл подкачки.

Поскольку драйверы ядра активно используют пулы для хранения внутренних объектов, их исследование представляет интерес при анализе состояния системы.

### 5.2. Pool Tags

Некоторые выделения памяти сопровождаются специальными четырёхсимвольными идентификаторами — **Pool Tags**. Они позволяют определить происхождение выделенной области и упростить диагностику использования памяти. Pool Tags используются разработчиками и исследователями для анализа поведения драйверов и системных компонентов.

Для исследования применяются:

- PoolMon;
- PoolMonX;
- WinDbg;
- специализированные средства анализа дампов.

В контексте BitLocker в исторических исследованиях упоминаются следующие идентификаторы:

| Pool Tag | Контекст исследований |
| --- | --- |
| `FVEc` | Исторические исследования структур BitLocker |
| `Cngb` | Исследования объектов, связанных с CNG |
| `dFVE` | Исследования компонентов обработки зашифрованных томов и дампов |

> **Важно:** наличие определённого тега не доказывает присутствие ключевого материала. Интерпретация зависит от контекста, версии Windows и конкретной реализации системного компонента.

### 5.3. Особенности исследования Windows 11

Windows 11 представляет отдельный интерес для исследования внутреннего устройства BitLocker. В разных сборках могут отличаться:

- структура объектов ядра;
- механизмы выделения памяти;
- поведение криптографических компонентов;
- реализация драйверов;
- расположение внутренних структур;
- способы обработки аварийных дампов.

Поэтому при публикации результатов необходимо указывать конкретную версию системы. Например:

```text
Operating System: Windows 11
Release: 24H2
Architecture: x64
Build: указывается фактический номер сборки
```

Необходимо также указывать установленные обновления безопасности.

### 5.4. Интерпретация обнаруженных структур

При анализе дампа важно отличать реальные системные объекты от случайных совпадений. Обнаружение последовательности байтов, похожей на криптографические данные, само по себе не является достаточным доказательством.

Для подтверждения результатов необходимо учитывать:

- контекст памяти;
- принадлежность области определённому компоненту;
- соответствие структуры ожидаемому формату;
- версию исследуемой операционной системы;
- результаты независимого анализа.

## 6. Исследование метаданных BitLocker

### 6.1. Структура метаданных

BitLocker хранит служебную информацию, необходимую для управления зашифрованным томом. Метаданные содержат сведения о конфигурации шифрования и механизмах защиты. В частности, они могут включать:

- идентификаторы алгоритмов;
- сведения о защитных механизмах;
- информацию о конфигурации тома;
- идентификаторы объектов;
- параметры, связанные с управлением ключами.

Изучение метаданных позволяет получить независимое представление о конфигурации исследуемого тома. Для работы с форматом BitLocker существует проект **libbde**:

- [Репозиторий libbde](https://github.com/libyal/libbde)
- [Документация формата BDE](<https://github.com/libyal/libbde/blob/main/documentation/BitLocker%20Drive%20Encryption%20(BDE)%20format.asciidoc>)

### 6.2. Идентификаторы алгоритмов

В метаданных BitLocker используется поле **Encryption Method**. В формате FVE известны следующие значения:

| Значение | Алгоритм |
| --- | --- |
| `0x8000` | AES-128-CBC с Elephant Diffuser |
| `0x8001` | AES-256-CBC с Elephant Diffuser |
| `0x8002` | AES-128-CBC |
| `0x8003` | AES-256-CBC |
| `0x8004` | AES-128-XTS |
| `0x8005` | AES-256-XTS |

Важно различать идентификаторы Encryption Method в метаданных тома и внутренние представления криптографических алгоритмов в структурах памяти Windows. Одинаковые на первый взгляд числовые значения могут иметь разный смысл в зависимости от контекста. Поэтому интерпретация обнаруженных данных должна выполняться с учётом спецификации соответствующей структуры.

### 6.3. Сопоставление метаданных с результатами исследования

Метаданные BitLocker позволяют проверить, какой алгоритм используется для конкретного тома. Это особенно важно при исследовании дампов памяти, поскольку предположение об алгоритме не должно основываться только на версии Windows или стандартных настройках системы.

При документировании результатов рекомендуется отдельно фиксировать:

1. версию исследуемой Windows;
2. конфигурацию BitLocker;
3. используемый алгоритм шифрования;
4. тип защитных механизмов;
5. сведения о состоянии исследуемого тома.

## 7. Методология экспериментального исследования

Для получения воспроизводимых результатов исследование должно проводиться по заранее определённой методологии. Одного обнаружения интересующей структуры недостаточно: необходимо зафиксировать условия эксперимента и обеспечить возможность независимой проверки выводов.

### 7.1. Подготовка исследовательской среды

Перед проведением эксперимента необходимо зафиксировать конфигурацию тестовой системы:

| Параметр | Что фиксировать |
| --- | --- |
| Операционная система | Windows 11 |
| Версия | Например, 24H2 |
| Сборка | Полный номер сборки |
| Архитектура | x64 или ARM64 |
| Процессор | Производитель и модель |
| Оперативная память | Объём и тип |
| UEFI | Версия прошивки |
| Secure Boot | Состояние |
| BitLocker | Состояние защиты |
| Алгоритм | Значение из метаданных |
| Инструменты | Названия и версии |

### 7.2. Документирование результатов

Для каждого эксперимента следует создавать отдельный журнал, в котором фиксируются:

- дата проведения;
- конфигурация системы;
- используемые инструменты;
- исходные файлы и контрольные суммы;
- обнаруженные артефакты;
- ограничения исследования;
- итоговые выводы.

### 7.3. Воспроизводимость

Результаты исследования должны быть представлены так, чтобы другой специалист мог понять:

- на каком оборудовании проводился эксперимент;
- какая версия Windows использовалась;
- какие инструменты применялись;
- какие ограничения существовали;
- на основании каких наблюдений сделаны выводы.

Если исследование затрагивает внутренние структуры памяти, необходимо отдельно отмечать, какие сведения подтверждены документацией, а какие получены экспериментальным путём.

### 7.4. Минимальный рабочий процесс

Порядок работы на копиях, а не на оригиналах дампа и образа тома:

1. Посчитайте SHA-256 исходных файлов и сохраните значения в журнале.
2. Определите версию и сборку ОС в дампе с помощью Volatility 3:

```bash
python3 vol.py -f memory.raw windows.info
```

3. Прочитайте метаданные тома утилитой `bdeinfo` из пакета libbde — она показывает метод шифрования и типы защитников:

```bash
bdeinfo volume.img
```

4. Сверьте метод шифрования из метаданных с тем, что вы видите в дампе (см. 6.3).
5. Запишите результат в журнал по шаблону из 7.2.

## 8. Ограничения и факторы, влияющие на результаты

Исследование оперативной памяти имеет ряд ограничений. Даже при наличии корректного дампа не всегда возможно получить полную картину состояния системы.

### 8.1. Время получения дампа

Состояние оперативной памяти зависит от момента создания снимка. После потери питания содержимое DRAM постепенно деградирует. Скорость потери данных зависит от характеристик микросхем, температуры и других физических факторов. Поэтому время получения дампа — важная часть криминалистической документации.

### 8.2. Управление памятью

Освобождённые участки памяти могут повторно использоваться операционной системой. Это усложняет идентификацию объектов и может приводить к неполному сохранению исследуемых структур.

### 8.3. Обновления Windows

Microsoft регулярно выпускает обновления безопасности и изменяет внутренние компоненты операционной системы. В результате могут изменяться:

- структуры драйверов;
- механизмы выделения памяти;
- внутренние объекты;
- криптографические компоненты;
- обработка аварийных дампов.

### 8.4. Аппаратные механизмы защиты

Современные процессоры могут поддерживать аппаратные механизмы шифрования оперативной памяти, например:

- Intel TME;
- AMD SME.

Эти технологии повышают устойчивость к определённым сценариям физического доступа к памяти. Однако их наличие не означает абсолютной защиты от всех способов исследования работающей системы. Эффективность зависит от аппаратной платформы, конфигурации и конкретной модели угроз.

## 9. Защита от атак с физическим доступом

Хотя BitLocker обеспечивает защиту данных на уровне накопителя, безопасность устройства зависит также от защиты работающей системы. Рассмотрим основные меры снижения риска.

### 9.1. TPM + PIN

Использование TPM совместно с PIN-кодом добавляет дополнительный фактор аутентификации при загрузке. Это повышает устойчивость системы к некоторым сценариям физического доступа и попыткам несанкционированной загрузки.

Однако важно понимать, что после успешной разблокировки тома необходимые для работы криптографические данные могут присутствовать в оперативной памяти.

### 9.2. Полное выключение системы

Если устройство не используется продолжительное время, рекомендуется выполнять полное выключение. Спящий режим и гибернация отличаются от полного выключения механизмами сохранения состояния системы, поэтому их не следует считать эквивалентными с точки зрения защиты оперативной памяти.

### 9.3. Secure Boot и защита загрузки

Рекомендуется:

- использовать Secure Boot;
- ограничивать загрузку с внешних устройств;
- защищать настройки UEFI;
- поддерживать актуальную версию прошивки;
- использовать доверенные загрузочные компоненты.

### 9.4. Аппаратная защита памяти

Использование аппаратных механизмов защиты памяти может повысить устойчивость к определённым физическим атакам. Однако их необходимо рассматривать как дополнительный уровень защиты, а не замену BitLocker и другим средствам безопасности.

### 9.5. Обновление Windows

Необходимо своевременно устанавливать обновления Windows, драйверов и микропрограмм. Отдельное внимание следует уделять уязвимостям, связанным с:

- BitLocker;
- обработкой аварийных дампов;
- драйверами ядра;
- криптографическими компонентами;
- механизмами загрузки.

Например, CVE-2025-21210 (CrashXTS) — уязвимость раскрытия информации в BitLocker, исправленная январскими обновлениями 2025 года; Microsoft оценивает её в 4.2 по CVSS и требует физического доступа к устройству. Это исправление не отменяет самого факта присутствия ключевого материала в памяти работающей системы. Актуальные сведения об уязвимостях необходимо проверять по официальным бюллетеням Microsoft.

## 10. Заключение

BitLocker — важный механизм защиты данных в Windows, обеспечивающий шифрование содержимого накопителей и управление доступом к ним. Однако у полнотомного шифрования есть фундаментальная особенность: после разблокировки тома необходимые криптографические данные должны быть доступны операционной системе. Именно поэтому исследование оперативной памяти интересно специалистам по цифровой криминалистике и информационной безопасности.

В ходе исследования необходимо учитывать не только архитектуру BitLocker, но и особенности управления памятью Windows, внутреннее устройство драйверов, версию операционной системы и аппаратную конфигурацию. Особенно важно не переносить результаты одной сборки Windows на другие версии без дополнительной проверки.

### Основные выводы

1. BitLocker использует многоуровневую архитектуру криптографических ключей.
2. После разблокировки тома криптографический материал становится доступен системным компонентам.
3. Внутренние структуры памяти Windows меняются между версиями и сборками.
4. Pool Tags могут помогать в исследовании памяти, но не являются самостоятельным доказательством наличия ключей.
5. Метаданные BitLocker позволяют независимо проверять конфигурацию шифрования.
6. Воспроизводимость и документирование экспериментов — обязательные условия качественного исследования.
7. TPM + PIN, Secure Boot и аппаратные механизмы защиты повышают безопасность устройства, но должны использоваться в комплексе.

Безопасность BitLocker определяется не только стойкостью криптографических алгоритмов, но и защитой операционной системы, аппаратной платформы и физического доступа к устройству.
